# v0.5.1 设计 — 媒体任务可取消 + 队列超时预算(关闭 v0.5.0 两处偏差)

> 对应 v0.5.0 设计 §风险/已知限制中的两处诚实偏差:
> ① 队列任务的本地 whisper 子进程超时仍为 60s(承诺 15min);
> ② running 任务不支持强杀取消(仅 pending 可取消)。
> 制定日期:2026-08-29。可并入尚未打 tag 的 v0.5.0,或作为 v0.5.1 补丁版。

## 目标与定位

```
偏差① 超时:   队列路径子进程预算 15min、同步路径保持 60s——超时所有权从 provider 上移到调用点
偏差② 取消:   running 任务可取消——AbortHandle 注册表 + 子进程 kill_on_drop + 条件 UPDATE 防竞态
```

两项共享同一个底层机制:**子进程随 Future 丢弃而终止(`kill_on_drop`)**。
取消(丢弃 future)与超时(超时后丢弃 future)在这一点上汇合,因此一并设计。

---

## 关键现状(已核实)

- **超时硬编码两处**(`whisper_cpp.rs`,均在 provider 内部):
  - `transcribe()` 第 123 行:`timeout(60s, cmd.output())`(whisper 子进程);
  - `run_ffmpeg_transcode()` 第 191 行:`timeout(60s, ...)`(音频转码,注释"与 whisper 同享 60s")。
  - provider 经 `Arc<dyn TranscribeCap>` 注册,**同步/队列两路共用同一实例**——
    这就是"按时承诺放宽需拆双实例"结论的来源。
- **cloud `WhisperProvider` 无任何超时**(reqwest 默认无限)——内联云端调用今天可能无限挂死
  (顺带修复,见 T2 附带收益)。
- **`cancel_media_task` 无条件翻转状态**(commands.rs:1444):对 running 任务调它会把
  实际仍在跑的任务标成 cancelled(状态说谎),子进程继续消耗 CPU——等于没有取消。
- **worker 无取消通道**:`run_task` 内联 await `execute_with_retry`,外部无法中断。
- **tokio 机制已具备**(版本核实):
  - `tokio::process::Command::kill_on_drop(true)`(process/mod.rs:664)——丢弃持 Child 的
    future 时杀死子进程;**默认 false**(丢 future 子进程继续跑),必须显式开启;
  - `JoinHandle::abort_handle()`(runtime/task/join.rs:307)——可存的取消句柄;
    `abort()` 在下一个 await 点丢弃任务 future → 触发 kill_on_drop。

## 根因分析

偏差①的根因不是"没有 15min 常量",而是**超时的所有权放错了层**:
超时是**调用上下文**的属性(前台速记要 60s 快速反馈;后台任务预算 15min),
却被固化在 provider(共享资源)里。偏差②的根因是**没有持有可中断执行的句柄**。

## 方案一:超时所有权上移(调用点持有预算)

### 决策

1. **provider 内部去超时**:`whisper_cpp.rs` 的 `transcribe()` 与 `run_ffmpeg_transcode()`
   删除 `timeout(60s)` 包装,改为 `Command::kill_on_drop(true)`——
   超时到期时调用方丢弃 future,子进程随之被杀(含 ffmpeg 临时 wav 场景,tempdir 兜底清理)。

2. **`transcribe_with_fallback` 增加预算参数**(壳层函数,非 trait,改动局部):
   ```rust
   pub(crate) async fn transcribe_with_fallback(
       ..., language: Option<&str>,
       budget: Duration,          // 新增:调用点的子进程预算
   ) -> Result<(Transcript, String), String> {
       tokio::time::timeout(budget,
           lmnotes_core::llm::transcribe_fallback::try_transcribe_with_fallback(...))
       .await
       .map_err(|_| format!("transcription timed out ({}s)", budget.as_secs()))?
       .map_err(|e| { eprintln!(...); e.to_string() })
   }
   ```
   - **内联路径**(create_voice_note / create_media_note):传 `60s`(语义不变;
     附带收益——内联云端调用首次获得 60s 上限,此前 reqwest 无超时可无限挂)。
   - **队列路径**(worker `execute_transcribe`):传 `15min`(兑现 v0.5.0 设计承诺)。
   - 预算覆盖整条 fallback 链(云端尝试+本地降级共享预算),不是每 provider 各 60s。

3. **内联视频抽音轨**(`extract_audio_track`,create_media_note 用)保持现状 60s——
   该路径面向短媒体(队列才承接长媒体),注释说明。

4. **不做 trait 级改动**:`TranscribeCap::transcribe` 签名不动(云 provider 本就无超时概念,
   mock/测试零改动)。若未来出现"同一 provider 需要每次调用不同超时"的第三场景,
   再评估 `transcribe_with_opts(opts)` 默认方法形态。

### 超时预算矩阵(实现后)

| 路径 | whisper 子进程 | ffmpeg 抽音轨/转码 | 云端请求 |
|---|---|---|---|
| 同步(速记/短媒体) | 60s(调用点) | 60s(调用点) | 60s(调用点,**新增**) |
| 队列(worker) | **15min**(调用点) | **15min**(调用点) | **15min**(调用点) |

### 测试(TDD)

- `build_whisper_cmd` Debug 断言含 `kill_on_drop: true`;
- `build_extract_audio_cmd` 同上;
- whisper_cpp 单测:模拟挂死 binary(临时脚本 sleep)→ 由调用方 timeout 杀——集成层,
  保留现有 wiremock 测试不回归即可;超时逻辑本身在壳层用 `tokio::time::timeout` 语义,
  以 `transcribe_with_fallback` 预算参数的单测覆盖(极小 budget + pending mock → 超时错误文案)。

## 方案二:running 任务取消(AbortHandle 注册表)

### 决策

1. **取消注册表**(壳层,managed state):
   ```rust
   #[derive(Default, Clone)]
   pub struct CancelRegistry(Arc<Mutex<HashMap<String, AbortHandle>>>);
   impl CancelRegistry {
       pub fn register(&self, id: &str, h: AbortHandle);
       pub fn abort(&self, id: &str);            // 不存在则 no-op
       pub fn unregister(&self, id: &str);
   }
   ```
   lib.rs 在 `manage()` 前构造,克隆进 `WorkerDeps`;`cancel_media_task` 经 `State` 访问。
   不引入 tokio-util(CancellationToken)——`AbortHandle` 是 tokio 自带原语,
   `abort()` 丢弃任务 future → `kill_on_drop` 杀子进程,与方案一共享底层机制。

2. **worker 执行结构改造**:
   ```rust
   // run_task 内:
   deps.cancels.register(&task.id, handle.abort_handle());
   let handle = tokio::spawn(execute_with_retry(deps, task));
   tokio::select! {
       res = handle => { /* done/failed 正常收尾 */ }
       // 取消经注册表 abort 触发:handle 被 abort → JoinError is_cancelled
       // 简化:不用 select,直接 await handle;cancel 命令侧调用 abort(),
       // worker 的 await 以 JoinError(cancelled) 返回 → 按取消收尾
   }
   deps.cancels.unregister(&task.id);
   ```
   即:**不需要 select!**。`cancel_media_task` 调 `registry.abort(id)` → worker 侧
   `handle.await` 返回 `JoinError::is_cancelled()` → 标记取消收尾。单并发语义不变
   (下一个任务在收尾后才开始)。

3. **`cancel_media_task` 重写**(三分支):
   ```rust
   // pending → 直接翻 cancelled(原逻辑,但现在要防 worker 已拉起:见竞态段)
   // running → cancels.abort(id);标记交给 worker 的 JoinError 收尾(见下)
   // done/cancelled → 幂等返回 Ok
   ```
   worker 收到 JoinError::is_cancelled 后:**条件 UPDATE 防竞态**——
   新增 `SqliteIndex::cancel_running_media_task(id) -> Result<bool>`:
   `UPDATE media_tasks SET status='cancelled' WHERE id=?1 AND status='running'`,
   以 rows>0 决定写取消还是保留已完成结果(消除"abort 时恰好完成"的竞态说谎)。

4. **pending 取消的竞态**:worker 可能刚把任务标 running。修正命令为先查状态:
   pending → 直接 UPDATE(带 `WHERE status='pending'`,rows=0 说明已 running → 走 abort 分支);
   running → abort。两分支都幂等。

5. **UI**:任务中心 running 行加「取消」按钮(现仅 pending);i18n 复用 `tasks.cancel`。

### 任务生命周期(实现后)

```
pending ──worker 拉取──▶ running ──成功──▶ done
   │                       │ ⛔ cancel(abort)──▶ cancelled(条件 UPDATE)
   ├── ⛔ cancel ──▶ cancelled
   └── (worker 重试中同 running 语义)
```

### 测试(TDD)

- `CancelRegistry` 单测:register/abort/unregister、abort 未知 id no-op、克隆共享视图;
- `cancel_running_media_task` 条件 UPDATE:running→true、done→false(不覆盖结果);
- `cancel_media_task` 状态机分支逻辑抽纯函数 `decide_cancel_action(current_status)`
  (pending/running/终态 三分支)单测;
- 端到端(手动):挂死 whisper 的临时 binary 场景下取消 running → 子进程消失
  (`tasklist`/活动监视器)、状态变 cancelled、worker 继续处理下一任务。

## 风险与对策

| 风险 | 对策 |
|---|---|
| kill_on_drop 在 Windows 上的行为 | TerminateProcess 强杀;临时 wav 在 tempdir,OS 兜底清理 |
| abort 与任务完成竞态 | 条件 UPDATE(WHERE status='running')以 rows 裁决;完成则保留 done |
| 去掉 provider 内联超时后忘包调用点 | transcribe_with_fallback 是唯一入口(voice/media/worker 三处全走),编译期可见;grep 断言无裸调 |
| 内联云端 60s 对慢端点过紧? | 云转录 60s 内未返回本就超出速记场景预期;任务中心/队列承接长任务 |
| ffmpeg 转码(whisper_cpp 内)超时上移后与 whisper 预算共享 | 同一 budget 覆盖整链(转码+转录共享调用点预算),语义=「本次转录总预算」 |

## 手动验证

1. 挂死 whisper(临时 sleep 脚本冒充 CLI)入队 → 任务中心取消 → 子进程消失、状态 cancelled、下一任务继续。
2. 队列投 5 分钟音频(本地引擎)→ 不再 60s 失败,15min 预算内完成。
3. 同步速记路径:挂死 CLI 时 60s 报「transcription timed out (60s)」,UI 可重试。
4. done 任务点取消 → 幂等 Ok,结果不被覆盖。
